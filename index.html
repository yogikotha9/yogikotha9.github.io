Case studies

Six engineering problems from these roles: what was wrong, what I built, and what changed.

U.S. Bank

Monolith to microservices, from scratch

Problem
The legacy audit application mixed postings, settlements, and re-authorization in one codebase, so every change was slow and risky.
Approach
Split it into Spring Boot services with their own entity models and shared modules, fronted by Spring Cloud Gateway and configured through Spring Cloud Config.
Result
Teams release services independently, and a failure in one service no longer takes down the platform.

U.S. Bank

Consistent transactions without a global lock

Problem
A posting touches several services, and a failure halfway through could leave them out of sync.
Approach
Implemented the Saga pattern over Kafka, with a compensating step for each action and Resilience4j circuit breakers on synchronous OpenFeign calls.
Result
Failed postings roll back cleanly, and every step is visible in Splunk through a shared trace ID.

Charles Schwab

An SDK partners actually want to use

Problem
Partner apps needed client portfolio data, but each integration was custom and hard to secure.
Approach
Designed a lightweight Java SDK over OAuth 2.0 client credentials and scoped JWTs, served through AWS API Gateway and Lambda.
Result
Partners connect through one documented, secure path instead of one-off integrations.

Charles Schwab

Fast portfolio reads at scale

Problem
Advisors and partners request the same portfolio summaries repeatedly, putting load on core systems.
Approach
Stored pre-computed snapshots in MongoDB, cached hot summaries in Redis, and pushed updates through Kafka events.
Result
Dashboards load from cache, and downstream systems handle far fewer repeat requests.

Fiserv

Screening payments in parallel

Problem
Running fraud rules one after another added latency to every payment.
Approach
Ran rules concurrently with CompletableFuture, fed by Kafka payment streams, and routed flagged cases to analysts over ActiveMQ.
Result
Lower screening latency for high-volume payments, with suspicious cases reaching analysts quickly.

Ernst & Young

Heavy analytics off the request path

Problem
Calculating returns by category, segment, and security type slowed the dashboard while users waited.
Approach
Moved calculations to RabbitMQ background jobs, stored results in MongoDB, and served widgets through GraphQL.
Result
The dashboard stays responsive while analytics run in the background.

How I work

Strengths and habits that carry over from one team to the next.

APIs, entity models, and shared modules designed before code, with clear ownership per service.

Event-driven by default

Kafka for streams and queues, RabbitMQ and ActiveMQ for point-to-point work, Saga for distributed transactions.

Security built in

Oracle and PostgreSQL for ledgers, Cassandra and MongoDB for high-volume or flexible data, Redis for hot reads.
